# Technology and conventions

## Stack (do not add frameworks without discussing first)
- Java 21, Spring Boot 3.5.x, Maven (use `./mvnw`)
- Spring AI 1.1.x MCP server (WebMVC, streamable HTTP at `/mcp`); tools are `@Tool` methods in `agent/BasMcpTools`
- Persistence: `JdbcClient` with hand-written SQL, Flyway migrations in `src/main/resources/db/migration`
- Databases: Neon PostgreSQL free plan (profile `neon`, credentials from git-ignored `.env.local`), embedded H2 in PostgreSQL mode (profile `demo`, default; and tests). Never choose a paid Neon plan or feature.
- ML: Smile 4.4 (logistic regression, trees, random forest, gradient boosting, Isolation Forest). Smile 5+ needs Java 25, so do not upgrade.
- Offline ML lab: `com.basintelligence.mllab` (Spring-free, run by `ml/run-ml-lab.sh`). Models are exported to `src/main/resources/models` with a model card; never edit artifacts or cards by hand.
- Deep learning inference: ONNX Runtime Java (CPU). Vision: OpenCV 4.9 (openpnp bundle). Documents: Apache Tika 3.
- UI: Thymeleaf + Bootstrap 5 + Chart.js, served from WebJars (no CDN). No inline `<script>`; the CSP forbids it.
- Security: Spring Security. Testing: JUnit 5, Mockito, AssertJ, MockMvc, Testcontainers (Docker optional).

## Commands
- Run (offline demo): `./mvnw spring-boot:run` then open http://localhost:8080 (engineer / engineer123)
- Run against Neon: `SPRING_PROFILES_ACTIVE=neon ./mvnw spring-boot:run` with the variables from `.env.example`
- Unit + integration tests: `./mvnw test`. Including PostgreSQL and outage tests (Docker): `./mvnw verify`. Load test: `./mvnw test -Pperformance`. See docs/testing.md.
- Every new failure mode gets a scenario test in `src/test/java/com/basintelligence/scenarios`. Keep sensor faults, anomalies, predictions and confirmed failures as separate events.
- Retrain and re-evaluate all ML models: `ml/run-ml-lab.sh` (stop the app first; uses about 400 MB)
- Rebuild the ONNX baseline model: `ml/.venv/bin/python ml/build_defect_model.py src/main/resources/models/defect-detector.onnx`

## Code conventions
- Package by feature: `machine`, `factory`, `users`, `telemetry`, `analytics`, `risk`, `ml`, `mllab`, `vision`, `knowledge`, `investigation`, `maintenance`, `agent`, `web`, `config`, `common`.
- Feature engineering for a trained model lives in one class in `ml/` and is used by both the lab and the API, so training and serving cannot drift.
- Model evaluation: choose models and thresholds on validation data only; report test metrics once. Split to avoid leakage (by engine, by load, stratified).
- Domain types are Java records. Keep algorithms (detectors, analyzer, diagnosis engine, BM25, chunker) as plain classes without Spring dependencies so they can be unit tested directly.
- Throw `NotFoundException` (404) or `InvalidStateException` (409) from services; controllers stay thin.
- Every state-changing action writes to `AuditService` with the acting user (`kiro-agent` for MCP calls).
- SQL must run on both PostgreSQL and H2 PostgreSQL mode. Use `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP WITH TIME ZONE`, `TEXT`. Never edit an applied migration; add `V<n>__description.sql`.
- Memory budget: the app should run with `-Xmx768m`. Avoid loading large models or whole tables into memory.
- Templates call record accessors with parentheses, e.g. `${m.code()}`, and use the `@fmt` bean for formatting.
